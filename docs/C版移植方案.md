## 1. ⚠️ 前置条件：**C 的工具链必须先定下来**（已实测，是硬阻塞）

`firmware\c51\build_c.ps1` 走 `C51 → BL51 → OH51`。2026-09-20 实测（造一个 24506 B 的 C 程序验证）：

| 工具 | 结果 |
|---|---|
| **C51.EXE**（编译器） | **无限额** —— 编译通过，`.obj` 18202 B，退出码 0，**0 错 0 警告**（生成 `code=5451`，是上限的 265%） |
| **BL51.EXE**（链接器） | **硬墙** —— `*** FATAL ERROR L250: CODE SIZE LIMIT ... EXCEEDED`，退出码 3 |
| **LX51.EXE**（扩展链接器） | **同样是硬墙**（2026-09-20 补测，见下）—— `RESTRICTED VERSION WITH 0800H BYTE CODE SIZE LIMIT`，`*** ERROR L250`，退出码 3，`.abs` 长度 0 |

> **补测记录（LX51，别重复试了）**：`D:\keli\C51\BIN\` 里除 `BL51.EXE` 还有 `LX51.EXE`（扩展链接器，
> 理论上支持 Code Banking / 无 2 KB 限制），一度看起来是条出路。**实测不行**：
> 用 `firmware\c51\_probe_size\big.c`（21 KB 源，`C51 big.c SMALL` → `code=4211`）分别链接：
>
> | 链接器 | 结果 |
> |---|---|
> | `BL51.EXE` | `Program Size: ... code=4211` 之后 `*** FATAL ERROR L250`，退出码 3 |
> | `LX51.EXE` | `RESTRICTED VERSION WITH 0800H BYTE CODE SIZE LIMIT; USED: 1064H BYTE (204%)` → `*** ERROR L250`，退出码 3 |
>
> ⇒ **两个链接器都是 `SN: Eval Version`，限额检查在各自的许可证模块里（`LIMIT: 0800H BYTES`），
> 换链接器绕不过去。** 复现命令（`_probe_size\big.c` 保留着）：
>
> ```powershell
> cd firmware\c51\_probe_size
> D:\keli\C51\BIN\C51.EXE  big.c SMALL
> D:\keli\C51\BIN\BL51.EXE big.obj TO big_bl.abs   # exit 3
> D:\keli\C51\BIN\LX51.EXE big.obj TO big_lx.abs   # exit 3，同样 L250
> ```

> ★★ **而且 C 版不能用汇编版那招绕过**：
> 汇编版是**单模块全绝对地址**（全 `ORG`、无 `EXTRN`），A51 清单里**就是最终机器码**，
> 所以 `tools\lst2hex.py` 能直接拼 hex；**C51 产出的是可重定位目标模块**，
> `.LST` 里是生成的汇编**但没有最终绝对地址** ⇒ **拼不出 hex**。

**⇒ 两条路（**当时**以为只能二选一，实际走了第三条 —— 见第 11 节）**：

| 路 | 代价 | 备注 |
|---|---|---|
| **① 正式 Keil 授权** | 拿到就能开工 | 你正在解决的"2KB 墙"正好就是这个解药；`main.c` 现有代码**一行不用改** |
| **② 换 SDCC** | 按第 3 节的映射表改语法；代码生成质量不同、体积要重新量 | 免费；且 SDCC 的 `.hex` 由 SDCC 自己产出，**根本没有 BL51** |
| **③ ★ 自己当链接器（最终选的）** | 写一个转换脚本 | **不需要授权、不改 C 源码、不动时序**；见第 11 节 |

> ✅ **这条"没定下来就不要动手"后来被第 11 节的第三条路解掉了** ——
> C 版**不能只是"翻译稿"**（`正式固件开发记录.md` 第九节）这个要求也满足了：
> 现在它是一条能烧、能跑的完整固件。

## 2. 现成的 C 地基（块①已经写好，可直接复用）

读 `main.c` 摸清了既有风格，**移植要沿用**：

| 做法 | 现有写法 | 为什么 |
|---|---|---|
| ISR 用独立寄存器组 | `void timer0_isr(void) interrupt 1 using 1` | `using 1` 让中断**不必保存主循环的 R0~R7**，省进出开销 |
| ISR 共享变量 | `static volatile unsigned char dirbits;` | 必须 `volatile`，否则优化器会缓存 |
| 位变量 | `static bit ena; static bit buzb = 1;` | 用 Keil 的 `bit` 类型（进位寻址区） |
| **P0 只在 ISR 里组装** | ISR 尾部 `a = 0x80 \| dirbits \| ...; P0 = a;` | ★ **架构铁律不变**：主循环只改 `dirbits/duty_a/duty_b/buzb` |
| PWM 分频 | `if (++pwm_div >= PWM_DIV) { ... }` | C 的 ISR 撑不住 99.8 µs，所以**每 5 个 tick 才刷一次** → **100 Hz**（汇编版是 500 Hz） |
| 原子读时基 | `ET0 = 0; ...; ET0 = 1;` | 读两个字节中间不能被中断打断 |
| 常量表 | `static const unsigned char code seg_tab[6]` | `code` = 放程序存储器 |

> ⚠️ **已知且已接受的差异**：**C 版 PWM 是 100 Hz，汇编版是 500 Hz**。
> 这是 `main.c` 里有意为之（C 的 ISR 进出开销大），**评审意见里"PWM 取 100~200 Hz"反而更合规**。
> 移植时**保持 100 Hz**，不要为了"和汇编一样"去调 —— 调了会挤爆 ISR 预算。

## 3. 语法映射表（决定"换 SDCC"的成本）

| 用途 | Keil C51（现在用的） | SDCC |
|---|---|---|
| 位寻址 IO | `sbit KEY_S3 = P3^4;` | `__sbit __at(0xB4) KEY_S3;`（或 `__sbit` + `P3_4`） |
| 位变量 | `static bit ena;` | `static __bit ena;` |
| 程序存储器常量 | `const unsigned char code tab[]` | `const unsigned char __code tab[]` |
| 中断 | `void f(void) interrupt 1 using 1` | `void f(void) __interrupt(1) __using(1)` |
| 片内扩展 RAM | `xdata` 指针 / `XBYTE[]` | `__xdata` 指针 |
| 绝对地址 IO | `XBYTE[0x0000]`（`absacc.h`） | `*(__xdata unsigned char *)0x0000` |
| 主入口 | `void main(void)` | `void main(void)`（同） |

> **`main.c` 里用到的 Keil 专有构造**（= 换 SDCC 的改动量）：
> `sbit`（9 处）、`bit`（3 处）、`code`（2 处）、`interrupt 1 using 1`（1 处）、`volatile`（若干）。
> **改动量不大、是机械替换**；真正的不确定是**代码生成体积**（要重新量）。

## 5. ★ 高风险点：XRAM 记录区必须生成 `MOVX @DPTR`，**绝不能是 `MOVX @Ri`** —— ✅ **已实测解除**

汇编版用 `MOVX @DPTR` 访问片内扩展 RAM（`0x0000~0x00EF`，240 B 记录区）。
**原因**：`MOVX @Ri`（以及 Keil 的 `pdata` 指针）**高 8 位地址取自 `P2`**，
而 **`P2` 整口是数码管段选 + D3** ⇒ **一用就把显示打花**。

### 实测（2026-09-20，用 C51 编译器直接编，看生成的汇编）

做法：写对照试验，两种"安全写法"和一种"危险写法"各来一份，用 `C51.EXE ... SMALL CODE` 编译，
在 `.LST` 的 `ASSEMBLY LISTING OF GENERATED OBJECT CODE` 里数 `MOVX`。

| 写法 | 实测生成的指令 | 判定 |
|---|---|---|
| **`XBYTE[a] = v;`**（`#include <absacc.h>`） | `MOV DPL,R7` / `MOV DPH,R6` / `MOV A,R5` / **`MOVX @DPTR,A`** | ✅ **安全** |
| **`unsigned char xdata *p`** 再 `*p = v` | `MOV DPL,R7` / `MOV DPH,R6` / **`MOVX @DPTR,A`** | ✅ **安全** |
| 读回：`*p` / `XBYTE[a]` | `MOV DPL,R7` / `MOV DPH,R6` / **`MOVX A,@DPTR`** | ✅ **安全** |
| ⚠️ **`unsigned char pdata *pp`** 再 `*pp = v` | `MOV R0,AR7` / `MOV A,R5` / **`MOVX @R0,A`** ← **高字节走 `P2`** | ❌ **禁止** |

- 安全写法那一轮：**4 处 `MOVX` 全是 `@DPTR`，一处 `@Ri` 都没有** ✅
- 危险写法那一轮：**确实是 `MOVX @R0,A` / `MOVX A,@R0`** ❌ —— 与文档里的警告**完全一致**

> ⇒ **结论：`XBYTE[]` 或 `xdata` 指针都可以用；`pdata` 绝对不能用。**
> **SMALL 模式下这两者都走 `MOVX @DPTR`，不需要为了它换内存模式。**

### 仍然要做的验证（便宜，但别省）

1. **写完 C 版后抽查一次**：`python tools\lst_sizes.py` 看不了指令，要拿 `.LST` 里 `MOVX` 那几行确认是 `@DPTR`；
   （或者照上面的做法编个小对照文件，永远留着这个结论。）
2. **上机验一次"录一段 + 回放"的同时盯数码管** —— 若显示花掉，就是踩了 `pdata`/`@Ri`。

## 6. 逐项技术难点与对策

| # | 难点 | 风险 | 对策 |
|---|---|---|---|
| 1 | **红外解码的时序**（`MEAS_LEVEL` 轮询量脉宽） | ★★★ **最高**：C 的循环每圈比 asm 慢得多，脉宽分辨率变差 | 见下面专题分析 |
| 2 | **ISR 时长** | 高：必须 **< 99.83 µs**（否则丢 tick、PWM 崩） | 沿用 `PWM_DIV` 分频思路；10 ms 分频也放**P0 写完之后**；实测/估算 ISR 时长 |
| 3 | ~~**XRAM 访问**~~ | ✅ **已实测解除**（第 5 节） | 用 `XBYTE[]` 或 `xdata` 指针 → 实测都是 `MOVX @DPTR`；**禁用 `pdata`**（实测 `MOVX @Ri`） |
| 4 | `delay_ms` 已知 bug | 中：按键不跟手 | **改成用 tick 计时**（汇编版就是这么做的），别用嵌套空循环 |
| 5 | **位变量与 `volatile`** | 中：优化器缓存 ISR 共享变量 | ISR 读写的一律 `volatile`；位变量用 `bit` |
| 6 | PWM 频率差异（100 vs 500 Hz） | 低：**已接受的既有差异** | **保持 100 Hz**，别去追平 |
| 7 | 10 ms 分频的**除法精度** | 低 | `PWM_DIV`-式计数器累加到 100（或 5×20），**避免用除法** |
| 8 | 常量表放 `code` | 低 | `const ... code` |
| 9 | **看不到生成的汇编**（排查时要） | 低但会耽误事 | `build_c.ps1` 用的是 `C51 ... SMALL DEBUG`，**`.LST` 里只有源码、没有汇编**。要看汇编请编一份 `C51 xxx.c SMALL CODE`（`CODE` 指令才把汇编写进 `.LST`）——本次解除 XRAM 风险就是这么看到 `MOVX @DPTR` 的 |

### 难点 1 专题：红外解码在 C 里够不够快？

**量级分析**（11.0592 MHz，1 机器周期 = 1.085 µs）：

| | 轮询一圈 | 相对 100 µs 的 tick | 对门限的影响 |
|---|---|---|---|
| 汇编版 | ~5 µs | 0.05 tick | 可忽略 |
| C 版（估） | ~15~25 µs | 0.15~0.25 tick | 位判据 `IR_BIT_TH = 11`（1.1 ms）→ 误差 **~2%** |

**结论**：引导码（9 ms / 2.25 ms）与位宽（0.56 / 1.69 ms）的门限都很宽，
**±0.25 tick 的误差完全可以接受** ⇒ **C 版作红外解码是可行的**。
⚠️ 但仍要**上机实测**：按遥控器，确认 `K=xx` 出得来、不丢帧（可复用 `diag\irdecode` 的思路，或临时开串口）。

> ⚠️ 另一个隐患：`MEAS_LEVEL` 必须**轮询得比 tick 快**。C 版若因为优化级别把循环展开/变慢，
> 极端情况下会**整圈跳过一次电平变化**。所以**编译优化级别要固定下来并写进文档**。

## 7. ★★ C 版的**结构性好处**（这条要写进报告）

移植不只是"为了老师能读代码"。**C 版天然消灭了我们在汇编里踩过的两类射程/栈陷阱**：

| 汇编里的坑（本项目实际踩过） | C 版 |
|---|---|
| **`ACALL` 只能在本 2KB 页内跳** —— 跨页就 `TARGET OUT OF RANGE`（这次报了 **10 处**） | 编译器自动选 `ACALL`/`LCALL`，**不存在** |
| **`LJMP` 进来的段用 `RET` 收尾** ⇒ 弹出没压过的地址 ⇒ 跳飞（这次导致"**按 8 完全不回放**"） | 调用约定由编译器管，**不存在** |
| `SJMP`/条件跳转 **±127** 射程（踩过 2 次） | 自动变长跳 |
| 手写 `PUSH/POP` 配平、栈深靠自觉 | 编译器管 |

⇒ **答辩口径**：C 版的价值 = **可读性 + 消除一类低级但致命的手写射程/栈风险**，
**且实测体积与汇编几乎相同**（块①：汇编 830 B vs C 855 B）。

## 8. 体积核对方法（"对照汇编版"怎么做）

**汇编版的 yardstick（已测好）**：

| 区域 | 字节 |
|---|---|
| 基础功能 ①~⑥ + 10 ms 地基 | **2006** |
| 创新功能 ⑦⑧ | **692** |
| 合计 2698 + `ORG` 空洞 42 | **2740** ✓ 与 BL51 `code=` 吻合 |

**逐例程对照**用现成工具（免自己写）：

```powershell
python tools\lst_sizes.py firmware\car\car_asm.LST        # 汇编版逐标号
python tools\lst_sizes.py firmware\c51\main.LST          # C 版逐函数
```

汇编版**最大的几个**（供对照时心里有数）：

| 字节 | 例程 |
|---:|---|
| 95 | `MAIN`（初始化） |
| 91 | `IRC_DONE`（含红外极性与 UART/Timer 初始化） |
| 62 | `IR_EDGE`（引导码判定） |
| 54 | `RS_GO`（录制采样主逻辑） |
| 45 | `PLAY_LOAD` |
| 38 | `REC_ENTER` |
| 36 / 34 | `T0_P0` / `T0_NR`（ISR 主体） |
| 34 | `ML_NOMODE`（模式分派） |

**核对判据**：C 版**逐函数**与汇编版**同数量级**（差 2 倍以内算正常）；
**总 `code` 若超过 2740 的 ~1.3 倍**就要回头查是不是写法不对（例如把 `bit` 写成了 `unsigned char`、把 `code` 表写成了 RAM 表）。

## 9. 执行顺序（每步都编译 + 记体积 + 上机）

**原则**：**按块移植，一块一验**（与汇编版当初一模一样的节奏），**不要一次写完**。

```
② 红外（含 MEAS_LEVEL/IR_RECV）
      ↑ 先做这块，因为它是唯一的高风险点；先证明"C 能可靠解码"
      ↓ 验证：按遥控器出 K=xx、方向键能开车
③ 模式状态机      → 验证：长按 S3 循环、数码管 L/t
④ 寻光             → 验证：手电照左右
⑤ 循迹             → 验证：★ 顺便把汇编版遗留的 P5 方向一起定案
⑥ 避障闸门         → 验证：15cm 右转 / <5cm 刹停锁存 / S4 长按开关
⑦ 录制（含 XRAM）  → ★ 验证：MOVX @DPTR（盯显示不花）；录一段
⑧ 回放             → 验证：跑通 + 遇障停车终止
最后：全量回归 T11 + 创新功能 §9 的 T1~T13
```

# 11. ★★ 实施结果：第三条路走通了 —— **自己当链接器**

> 2026-09-20 晚。**用户拍板**：后续联调优化都在 C 版上做，所以 C 版必须能烧；
> 联调路线选"自己当链接器"。

## 11.1 一句话

**链接器（BL51 / LX51）只干"排地址"一件事，那就自己排。**
把 C51 生成的可重定位汇编（`.SRC`）拼成**一个绝对地址模块**，
交给 A51（评估版无限额）汇编 —— 它的清单里就是最终机器码 —— 再用现成的
`tools\lst2hex.py` 出 hex。

⇒ **C 源代码一行都没为工具链妥协，编译产物和原来的完全一致，时序不用重测。**

## 11.2 为什么可行（四条实测依据，不是推测）

| # | 依据 | 怎么测的 |
|---|---|---|
| 1 | `.SRC` 里 **0 条 `ACALL`、134 条全 `LCALL`** | 直接数 `main.src`；跨函数调用全是长调用 ⇒ **段序可以任意排**，不怕 2 KB 页 |
| 2 | **275 个 `?Cxxxx` 局部标号，去重后仍是 275** | C51 用的是全局唯一编号 ⇒ **合并成一个模块不会重定义** |
| 3 | 模块**只引用 1 个外部符号**：`?C_STARTUP` | 数 `EXTRN`。启动代码自己写十几行即可；原来那个 `?C?IMUL` 已在源码里消掉（见 11.7） |
| 4 | **DATA 56 B + 位变量 8 位** | 数 `.SRC` 的 `DS`/`DBIT` ⇒ 放得进内部 RAM |

> ⚠️ 第 1 节原来说"**C 版不能用 `lst2hex` 那招绕过**" —— 那句话的前提是
> "**等链接器排地址**"。地址我们自己排，这招就成立了。

## 11.3 构建链与三个工具

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File firmware\c51\build_c_abs.ps1
```

| 步 | 做什么 | 工具 |
|---|---|---|
| 1 | `main.c` → `main.src`（可重定位汇编源码） | `C51.EXE ... SMALL SRC` |
| 2 | `main.c` → `main.lst`（**带目标码**的清单，供体积/校验用） | `C51.EXE ... SMALL DEBUG CODE` |
| 3 | `main.src` → `main_abs.asm`（**排地址**，替代链接器） | **`tools\c51_link.py`**（新） |
| 4 | `main_abs.asm` → `main_abs.LST`（最终机器码） | `A51.EXE`（无限额） |
| 5 | `main_abs.LST` → `main.hex` | `tools\lst2hex.py`（现成） |
| 6 | 校验：体积 + **逐函数一致性** | **`tools\c51_sizes.py`** + **`tools\c51_verify.py`**（新） |

> ⚠️ **第 1、2 步都要跑**：带 `SRC` 时 C51 **不生成目标模块，清单里也没有汇编清单**
> （报 `NO OBJECT MODULE REQUESTED`），所以拿体积的那份清单必须单独再编一次。

## 11.4 内存布局（`tools\c51_link.py` 顶部可改）

| 区域 | 地址 | 内容 |
|---|---|---|
| 复位 | `0000H` | `MOV SP,#7FH` + `LJMP main`（自己写的启动，替代 `?C_STARTUP`） |
| 中断向量 | `000BH` | `LJMP timer0_isr`（**C51 自己在 `.SRC` 里给的**，脚本原样搬过来） |
| 代码 | `0010H` 起 | 54 个函数段 + 常量表，按 `.SRC` 段序连续摆放 |
| 数据 | `0030H` 起 | 46 个 `DS` 变量，共 56 B |
| 位 | `20H.0` 起 | 8 个 `DBIT` 变量 |
| 栈 | `SP=7FH` | 压栈先加后存 ⇒ 实际用到 **80H~FFH**（间接寻址区，本工程没往那儿放变量） |

## 11.5 ⚠️⚠️ 上机必读的两个高风险点（**红外那一项还没验**）

> ★ **上机请照 `docs\C版上机测试清单.md` 走** —— 那份把下面两条排成"第一/第二个要验的"，
> 并给了**诊断版 hex 的用法**（`build_c_abs.ps1 -Debug`）与**串口判读表**。

| # | 风险 | 为什么 | 上机怎么看出来 |
|---|---|---|---|
| 1 | **红外解码在 C 里够不够快** | `meas_level()` 每圈要读一次时基；C 比汇编慢，若循环太慢会**整圈跳过一次电平变化** | 按遥控器：能不能出 `K=xx`、方向键能不能开车。**这是上机第一件事** |
| 2 | **中断服务程序时长** | `timer0_isr` 占 129 字节；必须远小于 99.83 µs，否则丢 tick | PWM 抖动 / 蜂鸣器音调怪 / 红外脉宽整体偏大 |

> ★ 纪律：`meas_level()` 里的时基读取**必须保持内联**，不要改成调用 `tick_get()`——
> 函数调用会把每圈耗时从几十个机器周期抬到上百个。
> `main.c` 里那里有注释点名。

## 11.7 踩过的坑（留给后人，别再踩）

| 现象 | 根因 | 处理 |
|---|---|---|
| `lst2hex` 报 **19 处同地址冲突** | `.SRC` 里 **C51 自己带中断向量**（`CSEG AT 0000BH` + `LJMP timer0_isr`），我又手写了一条 ⇒ 位置计数器被拽回 `000B`，后面的代码盖到了常量表上 | 脚本改为**把 `.SRC` 里的向量原样接管**，自己不再硬编码 |
| 模块里冒出 `?C?IMUL` | 记录地址 `索引 × 3` 是 16 位乘法，编译器去调库 | 源码改成**移位加法**（`REC_ADDR` 宏） |
| 需要 C 运行期初始化段 | `static bit buz_quiet = 1;` 有静态初值 | 改成**不写初值**，由 `init_all()` 置 1（它在开中断之前跑） |
| `C51 ... SRC` 编完 `.lst` 里没有汇编清单 | 带 `SRC` 时不生成目标模块 | 分两次编译（见 11.3 的 ⚠️） |
| 逐函数比对出现 3 处不等（`apply_gear` +5 / `d_20ms` +10 / `ms10_get` +12） | C51 把**共享尾代码**另列成 `L?xxxx` 块且**没有 END 标记**，而 A51 排完地址后这些字节自然算在前一个函数名下 ⇒ **两边归属口径不一致**（总数其实相等） | `c51_verify.py` 统一口径：只在**真函数** BEGIN 时切换归属 |

## 11.8 复核方法（谁都能重跑）

```powershell
# 1) 一条命令走完全程（含校验，任一步不过就报错退出）
powershell -NoProfile -ExecutionPolicy Bypass -File firmware\c51\build_c_abs.ps1

# 2) 单看某一项
python tools\c51_sizes.py  firmware\c51\main.lst --top 20   # C51 逐函数体积
python tools\c51_verify.py firmware\c51\main.lst firmware\c51\main_abs.LST
python tools\lst2hex.py    firmware\c51\main_abs.LST firmware\c51\main.hex
```

**校验链的四个关口**（都通过才算成功）：
1. C51：**0 错 0 警告**
2. A51：**0 错 0 警告**
3. `lst2hex`：**同地址冲突 0 处**（这条能抓住"段摆重叠了"）
4. `c51_verify`：**54 个函数逐字节数完全一致**（这条能抓住"排地址改动了代码"）

当前实测：`bytes emitted 2917`、地址范围 `0000..0B8B`、
hex **184 条记录、校验和 0 错**。

**已知的空洞**（正常，不是问题）：`0006..000A`（复位向量与 T0 向量之间）和
`000E..000F`（T0 向量与代码起点之间）未编程，STC-ISP 烧录时保持 `FF` 即可。
