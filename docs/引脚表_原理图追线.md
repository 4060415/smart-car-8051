## 0. 这份表怎么来的（为什么可以信，以及怎么复现）

### 0.1 一个被推翻的旧结论

`docs\参考资料挖掘结果.md` 原来写"整份原理图没有任何字体对象，所有标号都是矢量线条描出来的轮廓，所以只能渲染成图再 OCR"。

**这是错的。** 真相是：

- 字体字典藏在**压缩对象流**（`/Type/ObjStm`，对象 1/3/4/5/13）里，直接对原始字节 grep `/Font` 当然返回 0；
- 页面 `/Contents` = 对象 **14~21**，里面有**真文字操作符**，例如：
  ```
  BT /TT2 1 Tf 0 4.4119 -4.4102 0 587.1 94.1306 Tm 0 Tc 0 Tw (C13)Tj ET
  BT ... Tm -.026 Tc (Z2)Tj T* -.0104 Tc [(11.)-18.8(05)13.6(92M)]TJ ET
  BT ... Tm .297 g -.0286 Tc (GND)Tj ET
  ```

所以每个标号都能被**精确提取成"文字 + 坐标"**，每条导线也都是**精确的矢量线段**。这比渲染成图再 OCR 可靠得多。

### 0.2 坐标与验证

- 页面 `/Rotate 90`、`MediaBox [0 0 595.22 842]`；渲染成 4250×3004 像素图时映射为
  `px = y_pdf × 5.0475`，`py = x_pdf × 5.0475`（原点左上）。
- 抽取结果与 `refs\schem_words.tsv`（旧 OCR）交叉验证：中位误差 **47 px**，其余三种旋转都是 900 px 以上 → 映射正确。
- 抽出：**1753 条线段 / 163 个结点圆点 / 341 个标号**。

### 0.3 判连接的规则（这是最关键的一步）

`docs\参考资料挖掘结果.md` 说得对：自动追线很容易把交叉线误判成连接。但**交叉其实是有标记的**——

- 两条线段**共享端点** → 连接；
- 一端落在另一条线**内部**，**且该处有结点圆点** → 连接；
- 只有**交叉**（两条线都是内部穿过）→ **不连接**。

> 有个坑：排阻 RN 的外框底边正好穿过它自己 8 个引脚的端点。如果"端点在线上就算连接"，整排阻会被短接成一坨。**必须要求结点圆点。**

### 0.4 两条"尺子"（用来定标号属于哪个引脚）

在本图上实测出来的排版规律，并且在 MCU 的 8 个引脚上验证过：

| 元素 | 规律 |
|---|---|
| 引脚号 | 锚点 y 在引脚线上方 **5.1 px** |
| 引脚名 / 网标号 | 锚点 y 在所属线上方 **5.1 px** |
| 元件符号内的引脚名 | 锚点 y 在引脚线下方 **7.3 px** |

验证：MCU 引脚号 `39/38/37/36/35/34/33/32` 的锚点 +5.1 算出来正好是 786.7 / 811.2 / 836.1 / 860.6 / 885.4 / 910.0 / 934.5 / 959.3 这 8 条引脚线，**一条不差**。

### 0.5 ⚠️ 已知的解析器坑（2026-09-17 已修，重要）

第一版抽取器漏了**所有用 `TJ`（带字距数组）画的文字**：标号总数只有 341，而实际是 **502**。

- 原因：`[(VC)26.4(C)12.8(B)-.8(AT)]TJ` 这种写法里，字符串先被收进操作数缓冲，
  然后遇到 `]` —— 而 `]` 被当成"操作符"，没匹配到任何分支，却仍然在循环末尾清空了缓冲，
  **把数组里的字符串全丢了**。只有简单的 `(x)Tj` 能抽到。
- 症状：`VCCBAT`/`USB5V`/`EA/VPP`/`RXD(P30)`/**L293D 的 `INPUT1~4`/`OUTPUT1~4`/`ENA`/`ENB`**、
  以及全部 `P35LC` 这类网标号，都读不到。
- 后果：曾导致两条**错误判断**——见第 4 节。
- 另外：**不要用 `grep` 在内容流里找文字**（`INPUT`、`L293`、`VCCBAT` 直接搜都是 0 处），
  因为字距会把单词拆成 `(VC)(C)(B)(AT)` 这样的碎片。必须真正解析操作符序列。
- 修复后标定误差从 47 px 降到 **31.5 px**（对 315 个标号）。

## 1. ✅ 确定

坐标均为 4250×3004 渲染图像素坐标。DIP40 脚号与端口名的对应也自洽（P0.0=39…P0.7=32，P1.0=1…P1.7=8，P2.0=21…P2.7=28）。

### 1.1 电机驱动（L293D = IC1，符号左边缘 x=2733.8）

| MCU | DIP40 | L293D | 引脚线 y | 判定依据 |
|---|---|---|---|---|
| **P0.0** | 39 | `INPUT1`(2脚) | 685.6 | 该网内含 L293D 引脚号 `2`，且共用端点 `(2733.8, 685.6)` |
| **P0.1** | 38 | `INPUT2`(7脚) | 784.3 | 引脚号 `7` |
| **P0.2** | 37 | `INPUT3`(10脚) | 808.8 | 引脚号 `10` |
| **P0.3** | 36 | `INPUT4`(15脚) | 907.5 | 引脚号 `15` |
| **P0.4** | 35 | `ENA`(1脚) | 932.1 | 引脚号 `1` |
| **P0.5** | 34 | `ENB`(9脚) | 956.9 | 引脚号 `9` |

连线形态（P0.0 为例，逐段坐标）：
```
(2124.75, 786.7) ──右──> (2543.9, 786.7) ──上──> (2543.9, 685.6) ──右──> (2733.8, 685.6) = INPUT1
```

**旁证（很强）**：P0.0~P0.7 **每一根**都挂着一个 **10K 排阻（RN）**的独立电阻，8 个电阻脚分别在
x = 2248.0 / 2272.5 / 2297.4 / 2321.9 / 2347.0 / 2371.3 / 2396.0 / 2420.6，公共脚在 x=2223.2 接 VCC。

> 这正说明 **P0 被当作输出用**——P0 是开漏口，驱动 L293D 必须外加上拉，设计者为此专门放了排阻。
> 反过来说，**"电机接 P1.0/P1.1/P1.4/P1.5"的旧推断是错的**（P1 上没有任何上拉）。

- `ENA`/`ENB` **不是跳线到 VCC**，而是由 MCU 控制 → 可以 PWM 调速。
- `OUTPUT1/OUTPUT2` → 电机 **M1**（位号 (3202.6, 720.1)）；`OUTPUT3/OUTPUT4` → **M2**（(3202.6, 843.3)）。
- **哪个轮子是左、哪个是右，图纸上没写**，只能实测；`config.h` 里留了 `LEFT_REVERSE` / `RIGHT_REVERSE` 开关。

### 1.2 蜂鸣器

| MCU | DIP40 | 链路 |
|---|---|---|
| **P0.6** | 33 | P0.6 ─→ **R2(1.5K)** ─→ **V1(S8550, PNP)** ─→ **SB1 蜂鸣器** |

判定依据：P0.6 的网远端落在 `(3531, 885)`，正是 R2 方框（3530.6~3579.7, 877.9~892.7）的左边缘，旁边标号 `1.5K`、`R2`。
V1 位号在 (3685.9, 872.7)、S8550 文字在 (3687, 882)。

> ⚠️ PNP 驱动 → **低电平发声**。

### 1.4 红外遥控接收（课题核心输入）

| MCU | DIP40 | 去向 |
|---|---|---|
| **P3.3 / INT1** | 13 | **红外接收头 0038 的输出** |

判定依据：IR 模块三个脚在 y = 1205.8 / 1168.9 / 1131.9（引脚号 1/2/3，`IR` 文字在 (653.2, 1213.1)）；
**P3.3 的网是一条从 x=692 到 x=1730 的直线，端点正好是 `(691.7, 1205.8)` = IR 第 1 脚**。

### 1.5 按键、循迹

| MCU | DIP40 | 去向 | 判定依据 |
|---|---|---|---|
| **P3.2 / INT0** | 12 | **S4**（+ R5 10K 上拉） | 线端 `(1015, 1132)`，与 R5(x≈1025)/S4(x≈1022) 同一纵向链 |
| **P3.4 / T0** | 14 | **S3**（+ R4 10K 上拉） | 线端 `(941, 1132)`，与 R4(x≈951)/S3(x≈948) 同一纵向链 |
| **P3.5 / T1** | 15 | **V2 循迹探头** + 220 + 15K + **R26(1.5k)** + **D5 阴极**；网标号 **`P35LC`** | 该网含 V2 符号 (1116,1901)、D5 阴极结点 (1162.9,1415.3)、R26 |
| **P3.6 / WR** | 16 | **V3 循迹探头** + 220 + 15K + **R27(1.5K)** + **D6 阴极**；网标号 **`P36RC`** | 该网含 V3 (1362,1901)、D6 阴极结点 (1409.1,1415.0)、R27 |
| **P3.7 / RD** | 17 | 网标号 **`P37ZC`**，线到 `(1824,1634)` / `(1739.8,1708.5)` | 板右侧 7 脚循迹接插件的 `ZC` 脚（靠网标号同名相连） |

> **网标号命名规律**：`P<端口><位><功能>` —— `P30RXD`(P3.0)、`P31TXD`(P3.1)、
> `P35LC`(P3.5)、`P36RC`(P3.6)、`P37ZC`(P3.7)、`P12EC`(P1.2)、`P13TR`(P1.3)、`P16`(P1.6)。
> 所以 **LC/RC/ZC 就是 P3.5 / P3.6 / P3.7**（同一根网在 MCU 侧和右侧接插件侧各有一个同名标号）。

> **D5 / D6 是循迹探头的信号指示灯**（不是电源灯）：
> `VCC → R26/R27(1.5K) → LED 阳极 → LED 阴极 → V2/V3 节点 = P3.5/P3.6`，**低电平点亮**。

> ⚠️ **电源提醒（原 B2 疑点，现已确认方向）**：MCU 的 VCC（第 40 脚）+ EA + 10K 排阻公共脚
> 属于同一个网，该网最上方 `(2149.3, 293.7)` 处有一个电源端口，旁边就是文字 **`VCCBAT`**
> （抽取坐标 `(2105.97, 288.58)`）。**即：MCU 吃的是电池轨，不是 USB5V。**

> （`USB5V` 是另一条独立轨，我没有找到它与 `VCCBAT` 之间的连接件——如需彻底确认请查 `S1` 附近。）
