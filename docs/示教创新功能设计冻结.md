# 1. 现状核对结果（★ 先看这里）

对冻结说明逐条核对，**发现 4 处与现有代码冲突/不符、2 处资源判断错误、1 处我自己上一份文档的错误**。

## 1.1 ❌ 冲突 C1：`MODE_PLAY` 若走现有避障闸门，行为与要求**正好相反**（最严重）

- 冻结说明 §9 要求：回放遇障 → **立即停车 + 终止复现**，"不擅自改变路径绕过去"。
- 实际代码 `MOTOR_SET_ACT`（L703–712）：

```asm
            MOV     A,      AVST
            DEC     A
            JZ      MSA_TURN                ; 1 = AV_TURN  近区 -> 改写成"原地右转避让"
MSA_TURN:   MOV     R6,     #ACT_RIGHT      ; ★ 把动作改写成"原地右转"（不是停车！）
```

- `AV_GATE`（L1805–1811）**只排除 `MODE_TRACK`**，所以新加的 `MODE_PLAY` 会被**自动纳入**并**改写成右转**。
- ⇒ 这**直接违反** §9。**必须让回放不走 `AV_GATE`**（方案见 §2.2）。

> ★★ **同时更正我自己上一份文档的错误**：`docs\创新功能方向评估.md` §3.2 写过
> "新加的 `MODE_PLAY` 不需要动 `AV_GATE` 一行，天然带避障" —— **那句话的结论对了（确实不用动 AV_GATE），
> 但理由是错的**：当时只想到"有没有避障"，没想到"避障的语义是**右转改写**"。
> 回放要的是"**停车终止**"，两者语义不同。已在 `创新功能方向评估.md` 加更正。
> （正确做法：**回放走独立分支，在 `AV_GATE` 之前就跳走**，于是 `AV_GATE` 仍不用改。）

## 1.2 ❌ 冲突 C2：`60H~7FH` **不是空闲 RAM，那是栈**

- 文档（`创新功能讨论输入包.md` §4、`开发前置信息.md`）写"`60H`~`7FH` 还剩 32 B"。
- 实际 `MAIN`（L286）：`MOV     SP,     #60H` —— 8051 **栈向上增长**，`PUSH` 落到 `61H`、`62H`…依次占用。
- ⇒ **`60H~7FH` 是栈区，不能拿来放变量**（放了会被 `ACALL`/中断 `PUSH` 踩掉）。
- ✅ **真正空闲的直接寻址 RAM = `21H`~`2FH`（15 B）**，外加位区 **`20H.4`~`20H.7`（4 位）**。
  已核验：`grep '\b2[0-9A-F]H\b'` 全文只有 `BIT 20H.0`~`20H.3`（`ENAB/ENBB/BUZB/DIAGNIB`），
  `21H~2FH` 无任何字节/位引用。
- ⚠️ 冻结说明 §4 没有提到 RAM 变量放哪，§5 只讲了 XRAM。**这一条是本次冻结新增的硬约束。**

## 1.3 ❌ 冲突 C3：回放若按主循环数节拍，**必然超报告 ±5% 指标**

- `IR_RECV`（L1038–1052）在没有红外信号时会**阻塞等到 25.6 ms** 超时。主循环手动路径（L429）与
  非手动路径（L388）**每趟都调它** ⇒ **主循环周期 ≈ 26 ms**，且它**不是常数**（收到帧时更久）。
- 若回放用"每趟循环 = 10 ms"来计时，误差达 **±26 ms**：一个 100 ms 的动作实际可能跑 126 ms = **26%**。
- 报告表 5 要求"每个动作持续时间误差 ≤ ±5%"。按 26 ms 抖动反推，**动作时长必须 ≥ 0.54 s 才达标**。
- ⇒ **必须**用 Timer0 中断里的 10 ms 软件基准（与冻结说明 §3.2 的要求一致），见 §5；
  并且回放期间**必须绕过 `IR_RECV` 的阻塞等边沿**，见 §6.3 `IR_RECV_NB`。

## 1.4 ⚠️ 冲突 C4：冻结说明 §8 的 `Motor_Set()` 在代码里**不叫这个名字**

- 报告与冻结说明写的 `Motor_Set(action, speed)`，实际函数名是 **`MOTOR_SET_ACT`**，
  入参是 **`A` = 动作码，`R7` = 档位 1~5（`R7=0` 即停车）**，**副作用会改 `R6`**（L700）。
- 同样，§8 提到的 `TICK_GET()` **确实存在**（L1271，出 `R4:R5`）。
- ⇒ 全文接口名以 §6 的真实清单为准。**不存在的函数名一律不用。**

## 1.8 ⚠️ 时间基准的精确值（报告数字需要更正）

- `T0_RELOAD = 164` ⇒ 每 tick = (256−164) × 12 / 11.0592 MHz = **99.83 µs**（不是 100 µs）。
- ⇒ **10 ms 基准 = 100 tick = 9.983 ms**，相对误差 **−0.17%**（远优于 ±5%）。
- ⇒ **单条最长 = 65535 × 9.983 ms = 654.2 s**。
  ⚠️ 报告写的是"655.35 s"（按理想 10 ms 算）——**严格说应是 654.2 s**，差 0.17%，建议报告按实际写。

## 1.9 ❌❌ 冲突 C5（**实施第一步就撞上**）：Eval 代码上限 2048 B 是**硬墙**，而 ⑦⑧ 装不下

**实测证据（2026-09-20）**：

| 步骤 | 结果 |
|---|---|
| 加"地基"（10 ms 分频 + 新变量清零 + 常量/表项）**之前** | `code=1930`（占上限 92%） |
| 加完之后 | **`code=2011`（96%）** ⇒ 只剩 **37 B** |
| ⑦⑧ 预估 | **+510~670 B** ⇒ 总计约 **2560 B** |
| **故意造 2650 B 探针**（`firmware\diag\sizeprobe.asm`）测上限是不是硬墙 | BL51 报 **`*** FATAL ERROR L250: CODE SIZE LIMIT IN RESTRICTED VERSION EXCEEDED`**，**退出码 3**，**不产出 `.abs`/`.hex`** |

⇒ **这是硬失败，不是警告。** 现有文档里"**体积已不再是约束（工具链上限用户自己解决）**"
（`README.md` §二、`正式固件开发记录.md` §8.3）**与实测不符**：本机工具链仍是 Eval 版，
且**全盘搜索确认**没有任何非 Eval 的 Keil、也没有 SDCC / ASEM-51 / 任何许可证文件。

### ✅ 解决办法（已实施，并逐字节验证）：绕开 BL51，用 A51 的清单直接生成 Intel HEX

**关键观察**：限额在 **BL51（链接器）**，**A51（汇编器）没有限额** ——
上面那个 2600 字节探针，**A51 汇编通过（0 错 0 警告）**，是 BL51 那一步才失败的。

`car_asm.asm` 是**单个绝对模块**（全部用 `ORG` 定位、无 `EXTRN`/`PUBLIC`），
所以 A51 已把地址全部解算完，**`.LST` 清单里就是最终机器码字节**。
→ 新增 `tools\lst2hex.py`：**`.LST` → Intel HEX**，把 BL51 + OH51 整个替掉。

**验证（它能被信任的唯一理由）**：对当前 `code=2011` 这一版，两条路各出一份 hex，逐字节比对：

```
python tools\lst2hex.py     firmware\car\car_asm.LST  car_asm_lst.hex
python tools\compare_hex.py car_asm_lst.hex           car_asm.hex
  -> IDENTICAL: the two images are byte-for-byte equal.
```

- 两边都是 **1969 字节**、范围 **0000..07DA**；
- 差的 42 字节正是 `ORG` 空洞（`0003..000A` 8 B + `000E..002F` 34 B）
  —— **1969 + 42 = 2011 = BL51 报的 `code=`** ✓ 完全对上。

**端到端验证**：`firmware\diag\sizeprobe.asm`（2650 B）走新 `build.ps1`：
BL51 报 L250 → **自动回退 `lst2hex.py`** → **成功产出 `sizeprobe.hex`（2605 字节）** ✓

### 已做的事

| 文件 | 改动 |
|---|---|
| `tools\lst2hex.py` | ★ 新增：`.LST` → Intel HEX；内置**同地址字节冲突检测**（有冲突则退出码 1） |
| `tools\compare_hex.py` | ★ 新增：两份 hex 逐字节比对（校验该工具的手段） |

| `firmware\diag\build.ps1` | 同上（镜像） |
| `firmware\diag\sizeprobe.asm` | ★ 新增：工具链探针（2600×`NOP`），复现"BL51 硬墙 + 回退可用" |

### ⚠️ 这条路的**限制**（必须知道）

1. **只适用于"单模块 + 全绝对地址"**。一旦引入 `EXTRN`/`PUBLIC` 或多模块分别汇编，
   `.LST` 就不再含最终地址，此路立刻失效 → 那时**必须换真工具链**。
2. **没有 BL51 的段重叠/重定位检查**。缓解：`lst2hex.py` 自己做**同地址冲突检测**；
   且本工程全绝对定位、`ORG` 由 A51 解析，风险很低。
3. **没有 `.M51` 内存映像**。但 BL51 仍会在失败前打出 `Program Size: ... code=NNNN`
   ⇒ **`code=` 数字照旧可读**（实测确认）✓
4. ⚠️ **C 版（`firmware\c51\`）大概率同样受限**（同一个 BL51），而它由 C51 编译。
   **待确认：`C51.EXE` 是否也限额。** 若也限额，C 版在验收前要一并解决 → 见 §7.5。

## 1.10 ❌ 实施中发现的**工具缺陷**（T0 抓串口时暴露，均已修）

这两条都不是新功能的问题，而是**"测键值的工具本身是坏的"** —— 这也正是
`docs\待办与风险.md` 里"遥控器录制/回放/清空三个键的码值还没实测"长期挂着的原因。

### 缺陷 T1：`diag\irdecode.asm` 的 32 位采样器**根本没在工作**（致命）

```asm
ISB_NEXT:   MOV  A,MASKB / RL A / MOV MASKB,A / JNZ ISB_DONE / MOV MASKB,#01H / INC PTRIDX
```

- `RL` 把 `80H` 转成 `01H`、**永远不为 0** ⇒ `JNZ ISB_DONE` **恒成立** ⇒ **`INC PTRIDX` 是死代码**；
- 而且这段推进写在 `IR_SETBIT` 里，而 `IR_SETBIT` **只在"这一位=1"时才被调用**。
- ⇒ 32 位全挤进 `IB0`，字节序号永远为 0 ⇒ 解出来**只可能是** `FF 00 00 00`（8 个掩码位全 OR 上）
  或 `00 00 00 00`（一个 1 都没有）—— **实测日志与之完全一致**。
- **修法**：按 `car_asm.asm`（**已上机验证可用**的解码器）的写法，把推进搬到 `IR_NEXTBIT`，
  改 `RLC` + `JNC`，**每一位都推**（对照 `car_asm.asm` 的 `IR_NEXTBIT`）。

### 缺陷 T2：`irdecode` 的 `L_CHK6` 是**死代码**

分发链是 `L_OK → L_NOTREP → L_CHK4 → L_CHK5 → L_SHOW`，**没有任何一条路跳 `L_CHK6`**
（该跳 `L_CHK6` 的地方写了 `L_CHK5`）。而 `IRSTAT=6`（"短引导码 + 数据段没过"）
**正好是这颗遥控器的失败方式** ⇒ 被当"静默"吞掉：**不响、不设 `HBSTAT`、不打原始 4 字节**
⇒ 心跳永远显示 `?`，**日志里查不出任何线索**（本次实测就卡在这里）。

### 缺陷 T3：文档里那条"临时改 `DEBUG_UART=1` 抓串口"的路**根本走不通**

`car_asm.asm` 开 `DEBUG_UART=1` **汇编不过**：报 **22 个 `TARGET OUT OF RANGE`**
（多出来的 ~434 B 调试代码把一批 `SJMP`/`CJNE` 短跳全推出 ±127 射程）。
⇒ 正确做法是**用 `diag\irdecode.hex`**（电机保持停转、专为读键值而写），**不要去动 `car_asm.asm`**。

### 处置与结果

| 文件 | 改动 |
|---|---|
| `firmware\diag\irdecode.asm` | 修 T1（掩码推进搬到 `IR_NEXTBIT`，`RLC`+`JNC`）+ 修 T2（改跳 `L_CHK6`）；重编 `code=1514`，0 错 0 警告 |
| `docs\遥控器码值表.md` | 补 7/8/9 = `42/52/4A` **实测确认**；加"irdecode 曾坏、已修"的警示与正确操作步骤 |
| `firmware\_serial_read_T0_keycodes.log` | 保留 T0 原始证据（`K=08 / K=42 / K=52 / K=4A`） |

**实测结果**：`K=42`（数字键 7）、`K=52`（数字键 8）、`K=4A`（数字键 9），
外加已知值 `K=08`（数字键 4）作为**自校验** ⇒ 读数可信，**D1 关闭**。

## 1.11 ❌ 实施中发现的**新坑**：`ACALL` 的 2KB 页限制（块⑦⑧ 写完才暴露）

块⑦⑧ 写完第一次汇编，报 **9 个 `TARGET OUT OF RANGE`**。查清后全部是同一个原因：

> **8051 的 `ACALL` 只能在"当前 2KB 页"内跳**（它只带 11 位地址，高 5 位沿用 PC）。
> 而块⑦⑧ 让 `code` 从 1930 涨到 2725 ⇒ 程序跨了 **3 个 2KB 页**，
> 于是"第 0 页的调用点"够不到"第 1 页的例程"，反之亦然。

**实测地址（从 `car_asm.LST` 读出来的）**：

| 例程 | 地址 | 所在页 |
|---|---|---|
| `BEEP` | `0x034D` | 第 0 页 |
| `D_20MS` | `0x081A` | **第 1 页** |

⇒ 出错的正是 `ACALL BEEP` / `ACALL D_20MS` / `ACALL PUT_HEX` / `ACALL PRT_ACTNAME` 这些
**跨页**的调用点。**修法：`ACALL` → `LCALL`（3 字节、能到任意地址）**，共改 **10 处**。

### 教训（下次加代码前先想这条）

1. **程序一旦超过 2KB（这里 2725 B，已跨 3 页），`ACALL` 就不安全了** ——
   新增代码一律用 **`LCALL`**，别图省一个字节。
2. ⚠️ **`SJMP`/`JZ`/`CJNE rel` 的 ±127 是另一回事**（本项目踩过 2 次）；
   `ACALL` 的 ±2KB 页是**第三个**射程限制，以前没遇到是因为程序没超过 2KB。
3. **定位办法**：A51 不把错误打到控制台，**错误在 `.LST` 里**（`*** ERROR #A51 IN <行> ... TARGET OUT OF RANGE`）。
   用 `grep ERROR car_asm.LST` 就能拿到行号。
4. **判断跨没跨页**：`grep` 一下 `.LST` 里 `ACALL  xxx` 那几行的 `LOC` 字段（就是调用点地址），
   和例程标签的 `LOC` 比一比页号即可 —— 比"猜"可靠得多。

> ★ 另一条**顺带发现**：`IF DIAG_IR` 里的那批 `ACALL`（第 2223~2286 行）**根本没被编进去**
> （`DIAG_IR=0`），所以它们**永远不会**报跨页错 —— 排查时别把它们算进"待修清单"。

### 实施中的两处**有意设计**（与冻结原文有出入，以本节为准）

| 项 | 冻结原文 | 实际实现 | 为什么 |
|---|---|---|---|
| **单条时长上限（D2）** | `REC_CAP = 3000`（30 s，按 16 位比较） | **`RECCAP_H = 0BH` 按"高字节"判定**，实际落在 **28.1~30.7 s** | 省掉 16 位比较（约 10 字节）；D2 要的只是"别让单条无限延长"，精度无所谓 |
| **超声波测距节流计时** | 未指定变量 | **复用 `SAMP_L/H`** | 15 B 直接寻址 RAM 已用满，而**录制与回放互斥**（回放时 `RECON=0`，`REC_SAMPLE` 不会跑），这两字节在回放期间是空闲的。**是有意复用，不是笔误**（代码里已标注） |

### 块⑦⑧ 的**声/光约定**（上机测试照这张表判读）

| 操作 | 蜂鸣器 | 数码管 |
|---|---|---|
| 按 `7` 进录制 | 响**一声** | `r` |
| 按 `7` 退录制 | 响**两声** | 回档位数字 |
| 按 `8` 进回放 | 响一声 | `P` |
| 回放**正常播完** | （无） | 回档位数字 |
| 回放**遇障终止** | 响**两声短** | 回档位数字 |
| 空记录时按 `8` | 响两声 | 闪 `E` |
| 录满 80 条 | 连响约 400ms | `F` |
| 按 `9` 清空 | 响**两声** | 回档位数字 |
| 录制中想切模式（被拒） | 响**两声** | **不变**（仍是 `r`） |

# 2. 冻结后的总体架构

## 2.1 一句话

在**不动电机层、不动避障闸门、不动红外解码、不动模式循环**的前提下，
新增一层**"示教记录层"**（叠加在手动模式上）与一层**"复现执行层"**（独立模式），
两者共用同一份 XRAM 记录区与同一个 Timer0 派生的 10 ms 基准。

```
                  ┌──────────────────────────────────────────┐
   红外遥控 ──► IR_RECV / IR_RECV_NB                          │
                  │                                           │
                  ▼                                           │
        ┌─────────────────────┐                              │
        │  手动路径（原有）    │  MODE = MODE_MANUAL           │
        │  DO_KEY / 松键超时   │  CURACT / GEAR  ← 唯一"意图"源 │
        └─────┬───────────────┘                              │
              │  RECON=1 时每趟采样                            │
              ▼                                               │
   ┌──────────────────────┐   写出    ┌───────────────────┐   │
   │ REC_SAMPLE / REC_COMMIT├────────►│ XRAM 0x0000~0x00EF │   │
   │ (10 ms 分频 + 合并)   │           │ 80 条 × 3 B = 240 B│   │
   └──────────────────────┘           └─────────┬─────────┘   │
                                                 │ 读出       │
   ┌──────────────────────┐                      ▼            │
   │ PLAY_STEP（独立路径） │◄─────────────────────┘            │
   │  ① PLAY_SAFETY 先查   │   MODE = MODE_PLAY(3)             │
   │  ② 到点 -> 取下一条   │                                   │
   │  ③ MOTOR_SET_ACT(A,G) │────► MOTOR_SET_ACT（原有，不改）──┘
   └──────────────────────┘            │
                                       ▼
                          DIRBITS / DUTY_A / DUTY_B  ──► T0_ISR 组装 P0（原有，不改）
```

## 2.2 ★ 两条关键架构决定

### 决定 A：**回放走"最前面的独立分支"，`AV_GATE` 与 `KEY_SCAN` 都不经过**

```asm
MAIN_LOOP:
            MOV     A,      MODE                 ; ★ 新增 3 条
            CJNE    A,      #MODE_PLAY, ML_NP
            LJMP    PLAY_STEP
ML_NP:
            ACALL   AV_GATE                      ; ← 以下全是原有代码
            ...
```

一举解决 4 个问题：

| 解决 | 说明 |
|---|---|
| **C1** 避障语义冲突 | 回放根本不进 `AV_GATE` ⇒ **`AV_GATE` 一行都不用改**；`AVST` 在回放入口显式置 `AV_FREE`，`MOTOR_SET_ACT` 就不会改写动作 |
| **C3** 节拍精度 | 回放路径不受 `IR_RECV` 的 25.6 ms 阻塞 ⇒ 主循环周期 ≈ 1 ms |
| **§10** 人工 Stop 优先级 | 回放自己解析遥控键（不经 `DO_KEY`）⇒ Stop 一等优先，不必与调速/模式键纠缠 |
| 板载按键阻塞 | 回放**不调 `KEY_SCAN`**（它长按判定会阻塞最多 1 s，会毁掉节拍）⇒ 也**顺带避免** `MODE_SWITCH` 在 `MODE=PLAY` 时 `INC` 越界取 `MODETAB[4]` 的风险（见 §8 R7） |

> ⚠️ **代价（必须接受）**：回放期间**板载 S3/S4 不响应**（人工终止只能用遥控）。
> 理由：`KEY_SCAN` 是阻塞式长按判定。此项列为**已知限制**，见 §8 R8。

### 决定 B：**`MODE_PLAY` 取值 3，`NMODES` 保持 3（不进模式循环）**

- `MODE_MANUAL=0 / MODE_LIGHT=1 / MODE_TRACK=2`（L104–106），`NMODES=3`（L107）。
- `MODE_SWITCH`（L1566–1570）：`INC A; CJNE A,#NMODES,MODE_GOTO; CLR A`。
  ⇒ 取 `MODE_PLAY = 3` 时，长按 S3 循环在 `MODE=2` 处 `INC→3 == NMODES` 就绕回手动，
  **永远选不到 3** ⇒ `NMODES` **不用改**，模式循环行为**一个字都不变**。
- `MODETAB`（L2152）按 `MODE` 索引取段码 ⇒ 只需**追加 1 个字节**（索引 3 = 回放代号），旧索引 0/1/2 不变。

### 决定 C：**"录制"是叠加标志，不是模式**（对报告表 2 的修正）

- 报告的"手动 / 动作录制 / 动作回放 / 安全停止"四态是**并列**的。
- 但按报告 §3.3，录制时遥控键**仍要驱动电机**（人得把车"开"给车看）⇒ 录制 = **手动模式 + `RECON=1`**。
- ⇒ `MODE` 保持 `MODE_MANUAL`，只置 `RECON` 位；**只有回放才是真正的第四个 `MODE`**。
- 建议在报告里改写为："状态机按**控制权归属**划分：录制是手动模式的**叠加**，回放是**独立模式**，
  安全停止是**可被任何状态进入的出口**"。**这是设计深度的体现，也是答辩可讲的点。**

## 3.3 `PLAY_EXIT` 的收尾（两个出口共用）

1. `MOTOR_SET_ACT(ACT_STOP, R7=0)` —— 停车；
2. `CURACT = ACT_STOP`（★ 必须自己清：`MSA_IDLE` **不清 `CURACT`**，见 L766，不清会让 D3 误亮"在动"）；
3. `MODE = MODE_MANUAL`；
4. `GEAR = PLAY_GEAR0`（**恢复进入回放前的档位**——否则"复现"改了用户的档位）；
5. `AVST = AV_FREE`（避障重新武装，下一趟 `AV_GATE` 会自己重算）；
6. `LASTCMD = LASTCMD_NONE`（允许同一个键再按一次）；
7. `ACALL SHOW_STATE`（刷回档位显示）。

## 3.4 优先级（按冻结说明 §10，映射到真实分支）

| 优先级 | 事件 | 在代码里的位置 | 实测可达延迟 |
|---|---|---|---|
| **1 最高** | **安全停止**（§9） | `PLAY_STEP` 第一步 `PLAY_SAFETY` | 检测到 → 电机断电 **≤ 1 ms** |
| 2 | 人工 Stop（`40H`） | `PLAY_STEP` 的键解析（`MOTOR_SET_ACT` 前置） | ≤ 主循环周期（≈1 ms）+ 解码 ≈ 26 ms |
| 3 | 人工方向键接管 | 同上 | 同上 |
| 4 | 障碍**检测** | `PLAY_SAFETY` 内：红外**每趟**、超声波**每 ≥60 ms** | 红外 ≤1 ms / 超声 ≤60 ms |
| 5 | 当前动作计时 | `MS10` 与 `PLAY_T0` 比较 | ≤1 ms |
| 6 最低 | 下一条记录 | 计时到点后 `PLAY_LOAD` | — |

> ★ **两个"延迟"必须分清**（报告里别混）：
> **"检测到 → 停车" ≤ 1 ms**；**"障碍出现 → 被检测到" ≤ 60 ms**（超声波测距周期，见 §8 R4）。

## 3.5 ★ 模式进入/退出：主方案与备用方案（冻结说明 §12 要求）

**约束回顾**：现有入口有 `S3`（短按加档 / 长按切模式）、`S4`（短按减档 / 长按开关避障）、
遥控（方向 5 键 + 数字键 1/2/3 直选模式 + 4/6 加减档）；数码管**只有 1 位**。

### 主方案 A（**推荐**）：遥控数字键 `7` / `8` / `9` 直选 —— `42H` / `52H` / `4AH`

| 功能 | 键 | 码值 | 进入 / 退出方式 |
|---|---|---|---|
| **录制** | `7` | `42H` | **按一下进、再按一下出**（切换式）。退出即封存 |
| **回放** | `8` | `52H` | 按一下**直接进 `MODE_PLAY`**；再按一下 / 按 `40H` 停止 / 按方向键 → 退出 |
| **清空** | `9` | `4AH` | 车停着时按一下清空 |

**为什么推荐**：

1. **与现有机制同构**——R14 已经建立了"遥控数字键直选"这条路（`KEY2MODE`，数字键 `1/2/3` = `0C/18/5E`）。
   `7/8/9` 只是**同一行排布的下三个键**，操作者的心智模型**不用重建**。
2. **面板上就是标着 `7` `8` `9` 的三个键**，好记、好讲、**答辩时一句话说清**。
3. **数码管一个字符够用**：`r`（录制）/ `P`（回放）/ `E`（空）/ `F`（满），段码已交叉验算（§3.1）。
4. **不与任何基础功能冲突**：`42H/52H/4AH` 与已用的 `46/15/44/43/40/5A/08/1C/0C/18/5E` **无重叠** ✅
5. **对既有代码改动最小**：只在 `DO_KEY` 开头加 3 个分支（M4），**不匹配时行为完全不变**。

**代价**：① 需核实码值（T0，30 秒）；② 录制中长按 S3 会切模式 → **已在 D3 解决：录制中禁止切模式**（风险 R16 见 §10.2-D3）。

### 备用方案 B：板载 `S3` 长按组合（**不推荐**）

例：手动模式下 `S3` 长按 ≥3 s 进录制，再长按退出。

| 优点 | 缺点 |
|---|---|
| 不依赖遥控、不动 `config.h` 键值 | ❌ **与现有"S3 长按 1 s 切模式"正面冲突**——必须改 `KEY_SCAN`（阻塞式长按判定，改它风险高）或 `MODE_SWITCH`（改已验证代码） |
| 遥控没电时也能用 | ❌ `KEY_SCAN` 的长按判定**本身阻塞最多 1 s**（现成风险 3），再加 3 s 门限会让盲区更长 |
| | ❌ 难记、难演示；板载只有 2 个键，**装不下 3 个功能**（录/放/清） |

### 备用方案 C：改用"码值已知、按键未知"的空闲码（**保底**）

用 `45H/47H/07H/09H/16H/19H/0DH` 中的三个。

| 优点 | 缺点 |
|---|---|
| 完全不依赖任何"行↔按键"推断 | ❌ **面板上没有已知对应的按钮** ⇒ 演示时必须现场试按，**违背"容易演示"** |
| `42/52/4A` 若实测不符时可直接退到这里 | ❌ 需要用户逐个按键对照串口日志找 |

### 备用方案 D：复用已废弃的"数字键 `5`"（`1CH`）

R14 之后 `1CH` 已无功能（按了等于"不认识的键"）⇒ **零冲突**。
但**只有一个键**，只够挂"录制"这一个功能，**装不下回放与清空**。可作为 A 的**补充**（例如 `5` = 备用录制键）。

### 结论

| 方案 | 改动既有多？ | 好演示？ | 好记？ | 冲突？ | 判定 |
|---|---|---|---|---|---|
| **A：`7/8/9`（`42/52/4A`）** | 仅 `DO_KEY` +3 分支 | ✅ 最短路径 | ✅ 与 1/2/3 同族 | 无 | ✅ **推荐** |
| B：`S3` 长按组合 | ❌ 要改 `KEY_SCAN`/`MODE_SWITCH` | ❌ | ❌ | ❌ 与切模式冲突 | ❌ |
| C：空闲码 | 同 A | ❌ 按钮未知 | ❌ | 无 | ⏸ 保底 |
| D：数字键 `5` | 同 A | ✅ | ✅ | 无 | ⏸ 只够 1 个功能 |

⇒ **冻结采用方案 A**；若 T0 实测发现 `42/52/4A` 与数字键 `7/8/9` 不符，**退回方案 C**（改 `config.h` 三行即可，本冻结其余设计不受影响）。

# 4. 数据结构

## 4.1 记录单元（**3 B**，与冻结说明 §4 一致）

```
偏移 0：Byte0 = (Action << 4) | (Gear & 0x0F)
偏移 1：Byte1 = Duration 低 8 位
偏移 2：Byte2 = Duration 高 8 位
```

| 字节 | 位 | 含义 | 取值 |
|---|---|---|---|
| **Byte0** | bit7~4 | **Action** 动作码 | `0`~`6`（见 4.2）；`0FH` 保留为"空"哨兵 |
| | bit3~0 | **Gear** 档位 | `0`~`5`（`0` = 停） |
| **Byte1** | bit7~0 | Duration 低字节 | — |
| **Byte2** | bit7~0 | Duration 高字节 | — |

**冻结说明 §4 的例子补全**：`Action=1, Gear=4, Duration=1250`
⇒ `Byte0 = 14H`（高 4 位 `1`、低 4 位 `4` ✅ 与你给的 `14H` 一致）
⇒ `1250 = 0x04E2` ⇒ `Byte1 = E2H`（低）、`Byte2 = 04H`（高）⇒ 记录 = `14 E2 04`。
（`1250 × 9.983 ms = 12.48 s`）

## 4.2 动作码（**直接复用现有 `ACT_*`，不新增一套**）

| Byte0 高 4 位 | 现有常量 | 含义 | 电机效果（`MOTOR_SET_ACT`） |
|---|---|---|---|
| `0` | `ACT_STOP` | 停止 | `DIR_STOP`，`DUTY_A=B=0` |
| `1` | `ACT_FORWARD` | 前进 | `DIR_FWD`，两轮同占空比 |
| `2` | `ACT_BACK` | 后退 | `DIR_BACK` |
| `3` | `ACT_LEFT` | 原地左转 | `DIR_LEFT` |
| `4` | `ACT_RIGHT` | 原地右转 | `DIR_RIGHT` |
| `5` | `ACT_ARC_L` | **弧线左转** | `DIR_FWD` + `DUTY_A` 按 `ARCTAB` 调小 |
| `6` | `ACT_ARC_R` | **弧线右转** | `DIR_FWD` + `DUTY_B` 按 `ARCTAB` 调小 |
| `7`~`F` | — | **保留**（未使用） | — |

## 4.3 地址换算

- 写第 `i` 条（`i = RECN`，`0`~`79`）：`DPTR = i × 3`
- 读第 `i` 条（`i = PLAYIDX`，`0`~`79`）：`DPTR = i × 3`
- 换算用 `MUL AB`（`A = i`, `B = 3` → `B:A = i×3`），
  **`MUL AB` 在现有代码里已有先例**（L969）✅。`i` 最大 79 ⇒ `237 = 0x00ED` ⇒ `DPH=00H, DPL=EDH` ✅ 不越界。

## 4.4 合并规则（冻结说明 §6）

> **合并条件：`(Action, Gear)` **同时**相同。**

- 打包成 `PACK = (Action<<4)|Gear`，**只比较这一个字节** ⇒ 合并判定 = 1 条 `CJNE`。
- ✅ `Forward Geer 3` ×3 → 合成 1 条；❌ `Forward Gear 3` → `Forward Gear 4` 因 `PACK` 不同（`13H` vs `14H`）**不合并**。
- ⚠️ **合并的例外**（必须写进文档）：① **前导 STOP 不记录**（见 5.3）；
  ② **Duration 溢出时**会把一条拆成两条同 `PACK` 的记录（见 5.4）——**总时长守恒，不是丢时间**。

# 5. 时间基准与 RAM 布局

## 5.1 10 ms 基准（新增在 `T0_ISR` 尾部）

```asm
T0_P0:
            ... MOV P0, A            ; ← 原有：先把 P0 组装完
            ; ---- ★ 新增：10 ms 软件基准（放在 P0 写完之后，绝不扰动 PWM 时序）----
            INC     MSDIV
            MOV     A,      MSDIV
            CJNE    A,      #100, T0_END     ; 100 tick × 99.83us = 9.983ms
            MOV     MSDIV,  #0
            INC     MS10_L
            MOV     A,      MS10_L
            JNZ     T0_END
            INC     MS10_H
T0_END:
            POP     ACC              ; ← 原有
            POP     PSW
            RETI
```

| 项 | 值 | 说明 |
|---|---|---|
| 分辨率 | **9.983 ms** | 报告写"10 ms"，实际 −0.17% |
| 最长可表示 | **654.2 s** | `65535 × 9.983 ms` |
| 溢出周期 | `65536 × 9.983 ms ≈ 654 s` | 用**模差值**比较，动作时长 < 654 s 时绝对正确 |
| ISR 增量 | 典型 **+4.3 µs**（99/100 个 tick 只走 3 条指令）；每 100 个 tick 多 ~11 µs | ISR 原约 60 µs，加后约 **64 µs < 99.83 µs** ✅ 余量 ~36 µs |
| PWM 影响 | **零** | 分频代码在 `MOV P0,A` **之后**，P0 写入时刻不变 |

> ⚠️ **要求实测确认**（列入 §9 测试 T11）：改完后确认 PWM 频率、蜂鸣器音调、红外解码**均无变化**。
> ⚠️ `MS10_L/H` 是**自由运行**的计数器，主循环读它必须**原子**（同 `TICK_GET` 的写法：
> `CLR EA` → 读两字节 → `SETB EA`）⇒ 新增 `MS10_GET`（出 `R4:R5`），**不得直接分两次读**。

## 5.2 直接寻址 RAM 布局（`DATA`）

**现状（实测）**：`20H.0~20H.3` 位已用；`30H~5FH` 已用；**`60H~7FH` 是栈**（`SP=60H`）。

**冻结分配（把空闲的 `21H~2FH` 共 15 B 一次用满，避免以后再挪）**：

| 地址 | 名字 | 用途 | 范围 |
|---|---|---|---|
| `20H.4` | `RECON` | 1 = 录制中（手动模式的叠加位） | bit |
| `20H.5` | `PLAYERR` | 1 = 上次回放因**安全**终止（供提示/诊断） | bit |
| `20H.6` | `RECFULL` | 1 = 已到 80 条上限 | bit |
| `20H.7` | `SPARE0` | 保留 | bit |
| `21H` | `MSDIV` | ISR：10 ms 分频计数 `0`~`99` | 1 B |
| `22H` | `MS10_L` | ISR：10 ms 时基低字节 | 1 B |
| `23H` | `MS10_H` | ISR：10 ms 时基高字节 | 1 B |
| `24H` | `PACK` | 待提交记录的 `(Action<<4)\|Gear` | 1 B |
| `25H` | `CUR_DUR_L` | 当前记录**已累计**时长低字节 | 1 B |
| `26H` | `CUR_DUR_H` | 当前记录已累计时长高字节 | 1 B |
| `27H` | `SAMP_L` | 上次采样时刻低字节 | 1 B |
| `28H` | `SAMP_H` | 上次采样时刻高字节 | 1 B |
| `29H` | `RECN` | **已提交**记录数 `0`~`80` | 1 B |
| `2AH` | `PLAYIDX` | 回放索引 `0`~`79` | 1 B |
| `2BH` | `PLAY_DUR_L` | 当前回放条目时长低字节 | 1 B |
| `2CH` | `PLAY_DUR_H` | 当前回放条目时长高字节 | 1 B |
| `2DH` | `PLAY_T0_L` | 当前回放条目起始时刻低字节 | 1 B |
| `2EH` | `PLAY_T0_H` | 当前回放条目起始时刻高字节 | 1 B |
| `2FH` | `PLAY_GEAR0` | 进入回放前的档位（退出时恢复） | 1 B |

**合计 15 B + 4 位 = 恰好用满 `21H~2FH` 与 `20H.4~.7`，无溢出** ✅（见 §8 R2 的余量告警）

> ★ **为什么用"累计 + 增量"而不是"`now − T0`"**：
> 主循环可能被 `KEY_SCAN` 长按判定阻塞最多 1 s（`D_20MS` 现成风险 3）。
> 用 `delta = now − SAMP; CUR_DUR += delta` 的方式，**阻塞期间的时间会被完整计入**（不丢），
> 而 `now − T0` 方式在计数器回绕时会**静默变短**——正是冻结说明 §11 禁止的现象。

## 5.3 XRAM 布局（`MOVX @DPTR`）

```
0x0000 ┌────────────────────────────────────────┐
       │ 记录区  240 B = 80 条 × 3 B            │
       │ 第 i 条地址 = i × 3                    │
       │   i=0   -> 0x0000..0x0002              │
       │   i=79  -> 0x00ED..0x00EF              │
0x00F0 ├────────────────────────────────────────┤
       │ 保留区  16 B（冻结说明 §5 要求）       │
0x00FF └────────────────────────────────────────┘
```

- **访问只允许 `MOVX @DPTR`**（`MOVX @Ri` 会把 `P2` 当高 8 位地址 → 打花数码管，冻结说明 §5 禁令）。
- `DPTR` 在主循环里是**安全**的：`T0_ISR` 不碰 `DPTR`（已核验 L884–937 只 `PUSH PSW/ACC`）✅
- 保留区用途（按需，冻结不动）：将来如需更多变量、或加"记录头（版本/条数/校验和）"时的落点。

## 5.4 Duration 溢出与边界（冻结说明 §11 全部覆盖）

| 情形 | 判据 | 处置 | 防的是什么 |
|---|---|---|---|
| ★ **单条时长上限**（D2） | `CUR_DUR >= REC_CAP`（**= 3000 = 30 s**） | **静默拆条**：提交当前条 + 以**同一 `PACK`** 另起一条（`CUR_DUR=0, SAMP=now`） | 前进锁定式导致单条无限延长（见 §8 R7）。**回放时与一条长记录完全等价**（`MOTOR_SET_ACT` 幂等、两条之间不停车无间隙）⇒ 演示无差别、总时长守恒 |
| **单条累计溢出** | `CUR_DUR + delta` 产生**进位** | `CUR_DUR = 0xFFFF` → **立即提交**该条 → `CUR_DUR=0, SAMP=now`，`PACK` 不变（**拆成两条，总时长守恒**） | 禁止静默变短 ✅ |
| **溢出时已满** | 上一行发生且 `RECN == 80` | 停录 + 停车 + 显示 `F` + 长响（= T6） | 越界写 ✅ |
| **满记录** | `RECN == 80` | 停止写入；封存；保留已有数据；提示 | 数组越界 ✅ |
| **空记录** | `RECN == 0` 时按回放键 | 拒绝回放：闪 `E`×2 + 两声短响，**不进 S2** | 死循环 ✅ |
| **回放索引越界** | `PLAYIDX >= RECN` | 正常结束（T8），**不做任何 XRAM 读** | 读到垃圾数据 ✅ |
| **前导 STOP** | `RECN==0` 且 `PACK==(STOP,Gear)` | **不创建记录**（省记录、演示干净） | 浪费记录 ✅ |
| **中途/结尾 STOP** | 已有非 STOP 记录后 | **一律记录**（报告表 5 要求序列里含"停止"） | 序列不完整 ✅ |
| **`RECN>80` 的理论可能** | 提交前先判 `RECN>=80` | 先判后写，**不依赖事后检测** | 越界 ✅ |

## 6.3 ★ `IR_RECV_NB` 为什么可行（关键设计论证）

现有 `IR_RECV` 的开头是"**阻塞等下降沿**"（`IRW_EDGE` 循环，最长 25.6 ms），
之后从 `IR_EDGE` 开始量引导码低电平。

`IR_RECV_NB` 只把那个**等待循环**换成**一次判断**：

```asm
IR_RECV_NB:
            MOV     CAP_L,  #0
            MOV     LEDLO,  #0
            MOV     LEDHI,  #0
            MOV     SHORTL, #0
            MOV     IRSTAT, #1
            JB      IR_IN,  IRNB_OUT        ; 空闲高 -> 没有帧，立即返回（不阻塞）
            LJMP    IR_EDGE                 ; 已在下降沿 -> 走原有解码流程，一行不改
IRNB_OUT:   RET
```

- 帧的引导码低电平有 **9 ms** 宽，而回放主循环周期 ≈1 ms ⇒ 最多晚 **1 ms** 才进入解码，
  量到的引导码低电平 ≈8 ms，仍在 `IR_LEAD_MIN=70`~`IR_LEAD_MAX=120`（7~12 ms）窗口内 ✅
- 若恰好在数据位的 0.56 ms 低电平处进入 ⇒ 量到 ~5 tick < 70 ⇒ `IRSTAT=2`（帧被拒），**无害**（下一趟继续）
- ⇒ **"障碍出现→被检测到"与"按键→被响应"都降到 ~1 ms 级**，且 **`IR_RECV` 本身一个字不改** ✅
